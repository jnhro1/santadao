# santadao 프로젝트 개요

> 출처: Ouroboros 인터뷰 `interview_20261102_043303`(2026-11-02)과 추가 요구사항 정리(2026-11-02)
> 표기 규칙: **결정**은 사용자가 정한 사항이고, **설계 제안**은 결정 사항을 구현하기 위해 정한 기본값입니다. 설계 제안은 바꿀 수 있습니다.

> 용어: 화면과 문서에서는 **비밀 코드**라고 부르고, API 필드·DB 컬럼·코드 식별자는 `pin`을 그대로 씁니다.

## 한 줄 요약

로그인 없이 쓰는 **연말 크리스마스 마니또 랜덤 추첨 웹 애플리케이션**.
주최자가 이벤트 이름과 참가자 이름을 입력하면 즉시 추첨됩니다. 시스템은 참가자별 비밀 코드를 발급하고, 주최자는 공용 링크와 각자의 비밀 코드를 개인적으로 전달합니다. 참가자는 공용 링크에서 자기 이름을 고르고 비밀 코드를 입력해 **자기 마니또만** 확인합니다.

## 사용 흐름

```
[주최자]
  1. 이벤트 생성: 이벤트 이름, 메모(선택), 참가자 이름 3~20명 입력
  2. 제출 즉시 추첨, 참가자별 비밀 코드 발급
  3. 생성 완료 화면: 공용 링크, 관리 링크, 이름별 비밀 코드 목록
  4. 공용 링크는 단톡방에 공유하고, 비밀 코드는 각 참가자에게 개인 메시지로 전달

[참가자]
  1. 공용 링크 접속: 이벤트 이름, 메모, 참가자 이름 목록이 보임
  2. 자기 이름 선택
  3. 주최자에게 받은 비밀 코드 4자리 입력
  4. 내 마니또(내가 선물할 사람) 이름 확인 (몇 번이든 다시 확인 가능)

[주최자, 나중에]
  관리 링크 접속: 이름별 비밀 코드 목록 다시 보기 (결과는 표시하지 않음)
  → 참가자가 비밀 코드를 잊으면 다시 알려줌
```

## 결정된 사항

### 접근과 인증
- **로그인과 이메일은 없습니다.**
- **비밀 코드는 시스템이 발급합니다.** 이벤트를 만들 때 참가자별로 자동 생성합니다.
  - 형식은 **숫자 4자리**입니다.
  - 주최자에게만 보여주고, 주최자가 각 참가자에게 직접 전달합니다.
  - 참가자가 비밀 코드를 정하거나 바꾸는 기능은 없습니다.
- **결과 확인 방법:** 공용 링크에서 **이름을 선택하고 비밀 코드를 입력**합니다.
- **관리 링크:** 생성 완료 화면에서 공용 링크와 별도로 관리 링크를 줍니다.
  - 관리 링크로는 **이름별 비밀 코드 목록만** 다시 볼 수 있습니다.
- **주최자 화면에는 추첨 결과를 표시하지 않습니다.** 생성 완료 화면과 관리 화면 모두 해당합니다.

### 이벤트 생성 입력
| 항목 | 필수 | 규칙 |
|------|------|------|
| 이벤트 이름 | 필수 | 1~30자 |
| 메모 (선물 금액 등 자유 텍스트) | 선택 | 최대 200자 |
| 참가자 이름 목록 | 필수 | 3~20명, 이름당 1~10자 |

- 인원수는 따로 받지 않고 **입력한 이름 개수**로 정합니다.
- **이름 중복 검사:** 앞뒤 공백을 지운 뒤 비교하고, 영문은 대소문자를 무시합니다. 예를 들어 `" 민수 "`와 `"민수"`, `Kim`과 `kim`은 같은 이름으로 봅니다.
  - 중복이 있으면 생성을 거부하고 다시 입력하라고 안내합니다.
- 저장하고 표시할 때는 공백을 지운 이름을 씁니다.

### 추첨 규칙
- **추첨 시점:** 생성 요청을 받으면 즉시 추첨하고 결과를 확정합니다.
- **재추첨은 없습니다.** 다시 하려면 이벤트를 새로 만듭니다.
- **자기 자신은 뽑히지 않습니다.**
- **각 참가자는 정확히 한 명에게 선물하고, 정확히 한 명에게 받습니다**(순열).
- **완전 랜덤 배정입니다.**
  - 상호 배정(A↔B)은 우연히 나오면 허용하지만, 일부러 짝을 짓지는 않습니다.
  - 하나의 원형 고리일 필요도 없습니다. 수학적으로는 랜덤 완전순열(derangement)입니다.

### 링크
- **공용 링크:** 짧은 랜덤 코드를 씁니다. 예: `/e/K7mQ2xPa`
- **관리 링크:** 주최자 전용 링크입니다. 형식은 아래 설계 제안을 참고하세요.

### 데이터 보관
- **삭제하지 않습니다.** 자동 만료나 삭제 기능은 없습니다.

### 화면 구성
- REST API를 만들고, **정적 HTML/JS 화면을 같은 애플리케이션에 함께 배포**합니다(`src/main/resources/static`).

## 감수한 위험

사용자가 알고 받아들인 위험입니다. 구현할 때 따로 막지 않습니다.

| 위험 | 내용 | 결정 |
|------|------|------|
| 주최자 열람 | 주최자는 모든 비밀 코드를 알고 있어서, 마음먹으면 남의 결과를 볼 수 있음 | 화면에 결과가 안 보이면 충분 |
| 비밀 코드 대입 | 틀린 비밀 코드 입력 횟수에 제한이 없음. 이름을 알면 4자리 비밀 코드(1만 가지)를 대입해 볼 수 있음 | 제한하지 않음 |
| 관리 링크 유출 | 관리 링크가 유출되면 모든 비밀 코드가 노출됨 | 링크를 추측할 수 없게 만드는 것으로 대응 (설계 제안 참고) |
| 데이터 누적 | 데이터를 삭제하지 않아 계속 쌓임 | 삭제하지 않음 |

## 인수 기준

### 이벤트 생성
| # | 기준 |
|---|------|
| AC1 | 이벤트 이름과 참가자 이름 3~20명으로 이벤트를 만들면 공용 링크, 관리 링크, 이름별 비밀 코드 목록이 응답된다 |
| AC2 | 이벤트 이름이 비어 있거나 30자를 넘으면 거부된다 |
| AC3 | 메모가 200자를 넘으면 거부된다. 메모는 생략할 수 있다 |
| AC4 | 참가자가 3명 미만이거나 20명을 넘으면 거부된다 |
| AC5 | 공백을 지운 이름이 비어 있거나 10자를 넘으면 거부된다 |
| AC6 | 공백을 지우고 대소문자를 무시한 기준으로 중복 이름이 있으면 거부되고, 중복된 이름을 알려준다 |
| AC7 | 발급된 비밀 코드는 모두 숫자 4자리이다 |

### 추첨
| # | 기준 |
|---|------|
| AC8 | 어떤 참가자도 자기 자신을 배정받지 않는다 |
| AC9 | 모든 참가자는 정확히 한 명에게 선물하고, 정확히 한 명에게 받는다 |
| AC10 | 같은 이름 목록으로 여러 번 만들어도 배정 결과가 매번 달라질 수 있다. 상호 배정도 나올 수 있다 |
| AC11 | 한번 생성된 이벤트의 배정은 바뀌지 않는다 |

### 결과 확인 (참가자)
| # | 기준 |
|---|------|
| AC12 | 공용 링크로 이벤트 이름, 메모, 참가자 이름 목록을 조회할 수 있다. 결과와 비밀 코드는 포함되지 않는다 |
| AC13 | 이름과 올바른 비밀 코드를 입력하면 그 참가자의 마니또 이름만 응답된다 |
| AC14 | 비밀 코드가 틀리면 결과 없이 오류가 응답된다. 같은 이름으로 다시 시도할 수 있다 |
| AC15 | 존재하지 않는 공용 링크 코드는 "이벤트를 찾을 수 없음"으로 응답된다 |

### 관리 (주최자)
| # | 기준 |
|---|------|
| AC16 | 관리 링크로 이름별 비밀 코드 목록을 다시 조회할 수 있다 |
| AC17 | 생성 응답과 관리 링크 응답 어디에도 추첨 결과(누가 누구의 마니또인지)가 포함되지 않는다 |
| AC18 | 공용 링크 코드로는 관리 정보(비밀 코드 목록)를 조회할 수 없다 |

## 설계 제안

결정 사항을 구현하기 위해 정한 기본값입니다. 바꾸고 싶으면 수정하면 됩니다.

### 식별자
| 항목 | 제안 | 이유 |
|------|------|------|
| 공용 링크 코드 | 영문 대소문자와 숫자 8자리, `SecureRandom` 생성, DB unique | 짧아서 입력하기 쉽고 추측이 어려움 (62⁸ ≈ 218조) |
| 관리 링크 토큰 | 영문 대소문자와 숫자 32자리, `SecureRandom` 생성, DB unique | 모든 비밀 코드가 노출되는 링크라 공용 코드보다 훨씬 길게 만듦 |
| 비밀 코드 | `SecureRandom`으로 0000~9999, 같은 이벤트 안에서 중복 없이 발급 | 주최자가 전달할 때 헷갈리지 않게 함 |

- 관리 링크로 다시 보여줘야 하므로 **비밀 코드는 해시하지 않고 저장**합니다.

### 추첨 알고리즘
- `SecureRandom` 기반 Fisher–Yates 셔플을 쓰고, 자기 자신이 배정된 사람이 있으면 다시 섞습니다(rejection sampling).
- 모든 완전순열이 같은 확률로 나옵니다. 평균 약 e(≈2.72)회 시도로 끝납니다.
- Sattolo 알고리즘은 하나의 원형 고리만 만들기 때문에 요구사항(상호 배정 허용)에 맞지 않아 쓰지 않습니다.

### 데이터 모델 (초안)
```
events
  id, name(30), memo(200, nullable), public_code(8, unique), admin_token(32, unique), created_at

participants
  id, event_id(FK), name(10), pin(4), manito_id(FK → participants.id, nullable), created_at
  unique(event_id, name)
```
- `manito_id`가 nullable인 이유: 참가자를 모두 저장한 뒤에 배정해야 합니다. 생성 트랜잭션 안에서 배정까지 끝냅니다.
- 이름 중복 검사는 애플리케이션에서 정규화(공백 제거, 소문자 변환)한 값으로 합니다.

### API (구현됨)
모든 응답은 `ApiResponse { code, status, message, data }` 형식입니다. 예: `{ "code": 200, "status": "OK", "message": "OK", "data": {...} }`, 실패 시 `message`에 사용자용 메시지, `data`는 `null`.

| Method | URL | 설명 | 성공 응답 `data` | 실패 |
|--------|-----|------|------------------|------|
| `POST` | `/api/v1/events` | 이벤트 생성과 추첨 | 201. `name, publicCode, adminToken, participants[{id, name, pin}]` | 400 (입력 오류, 이름 중복, 이름 길이) |
| `GET` | `/api/v1/events/{publicCode}` | 공용 정보 조회 | 200. `name, memo, participants[{id, name}]` | 404 (이벤트 없음) |
| `POST` | `/api/v1/events/{publicCode}/reveal` | 결과 확인. 요청은 `{participantId?, name?, pin}` | 200. `manitoName` | 400 (비밀 코드 형식), 401 (비밀 코드 불일치), 404 (이벤트·참가자 없음) |
| `GET` | `/api/v1/admin/events/{adminToken}` | 관리 정보 조회 | 200. `name, publicCode, createdAt, participants[{id, name, pin}]` | 404 (이벤트 없음) |

- 에러 코드 전체 목록은 `global/exception/ErrorCode.java`에 있습니다.
- Swagger UI: `/swagger-ui.html`

- 비밀 코드가 URL이나 로그에 남지 않도록 결과 확인은 `POST` 본문으로 받습니다.
- 정적 화면:
  - `/`: 이벤트 생성
  - `/e/{publicCode}`: 참가자 화면
  - `/admin/{adminToken}`: 관리 화면
- 화면 경로 `/e/{publicCode}`, `/admin/{adminToken}`은 `WebConfig`가 각각 `event.html`, `admin.html`로 forward합니다.
- Spring Security는 모든 경로를 `permitAll`로 열고, CSRF·폼 로그인·세션을 끕니다. 로그인 없는 서비스라 필요하지 않기 때문입니다.

- [ ] 결과 화면에 마니또 이름 외에 이벤트 메모를 함께 보여줄지 (기본값: 함께 표시)

- [ ] 예상 트래픽 규모 (기본값: 소규모, 별도 대비 없음)
